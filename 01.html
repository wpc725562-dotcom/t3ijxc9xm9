四条结论（这就是你修改的底气）

① 你打算删掉的那些功能，同类项目里一个都没有。
在 MiloTnT（6 表）、liujianview（11 表）、bsxj97 的 源码文件树 + 建表脚本中逐一检索「签到 / 人脸 / 扫码 / 核销 / 候补 / 微信 / 短信 / 二维码」， 命中数全部为 0。删除它们不是「降低标准」，而是回到这类项目的真实水平。 方法：拉取 repos/<repo>/git/trees/<branch>?recursive=1 与 *.sql 后本地 grep（避免 GitHub 中文代码搜索失效）
② 有人真的「声明了却没实现」，这就是反面教材。
bsxj97 的 pom.xml 里赫然写着百度人工智能 SDK com.baidu.aip:java-sdk:4.4.1（人脸识别用的）， 但整个源码树里没有任何 face / aip 相关文件，Java 文件只有教练、用户、评论、收藏、分类、新闻、健身项目。 依赖声明了，功能从来没做 —— 答辩被问「人脸识别怎么做的」会当场露馅
③ 「签到」的正确形态是「一张表 + 后台手工登记」。
唯一实现了签到的 evangui（410★），做法是： 一张 CheckinRecord 表 + 标准增删改查（Controller / Service / Mapper / 页面）， 菜单挂在「会员」模块下，包含列表 / 添加 / 更新 / 删除 / 详情五个动作。 表字段里有 opeUserId、opeUsername（操作人）—— 这本身就是「工作人员手动完成签到」，没有任何扫码或人脸。 guns-admin/sql/CheckinRecord.sql + guns-bizcore/.../model/CheckinRecord.java
④ 同类项目清一色 Spring Boot 2.x，前端是 JSP/Bootstrap 或 Vue 2。
实测版本：2.0.3 / 2.2.2 / 2.5.3，没有一个用 3.x； 唯一用 Vue 的那个是 Vue 2.6.10 + element-ui 2.13，不是 Vue 3。 含义：你写「Spring Boot 3 + Vue3」是领先于参考项目，不是套话 —— 但要准备好回答代价（见 2.3）
⚠️ 顺带一个方法论提醒

GitHub 的中文代码搜索是不可靠的。我用 gh search code --repo X "签到" 查，返回空；改用「会员」「教练」「课程」这些必然存在的词做正对照， 同样返回空 —— 说明是查询失效而不是「没有这个功能」。 如果当时直接采信，就会得出「所有项目都没签到」的错误结论（恰好蒙对，但推理是错的）。 可靠做法是拉文件树和 SQL 后本地 grep。

2逐条修改对照表

2.1 研究背景 —— 删括号注释与分号，保留政策引号

修改前（典型写法）

近年来，随着「全民健身」国家战略的深入推进，我国健身行业迎来快速发展（全口径）； 同时，居民健康意识不断提升（全口径），传统健身房管理模式已难以满足需求； 因此，研究本系统具有重要的现实意义。

修改后

随着「全民健身」国家战略的推进，健身房数量持续增长，会员信息、课程预约、器材使用等日常事务的处理量随之增加。

目前多数中小型健身房仍依靠纸质登记或电子表格记录，存在查询不便、记录容易遗漏的问题。

因此，开发一套面向中小型健身房的管理系统具有实际应用价值。

为什么这样改

  • 括号注释是「自我防御式写作」。「（全口径）」这类词的作用是显得严谨， 但它既不是数据来源、也不是限定条件，读者无法验证。删掉后信息量不减，可信度反而上升。
  • 分号串句是 AI 的典型节奏：一个长句里塞三四个并列分句，靠分号连接，读起来很「全」但落不到具体对象。 拆成三个短句后，每句只讲一件事。
  • 「全民健身」的引号必须留 —— 这是有出处的政策表述（《全民健身计划》）， 加引号表示引用官方提法，属于有效引号；而「（全口径）」是无效括号。两者性质不同，不要一起删。
进一步强化：把「意义」换成「场景」

「具有重要的现实意义」是空话。改成可核查的场景描述，答辩时可以直接指着说。 例如：「前台查询会员到期时间，由翻阅纸质台账改为一次检索」。 凡是能被追问「具体体现在哪」的表述，都要落到一个动作上。

2.2 研究意义 —— 删连接词，「第一第二第三」改「(1)(2)(3)」

修改前（典型写法）

首先，提高管理效率。其次，降低运营成本。再者，提升用户体验。第一，……第二，……第三，……

修改后

(1) 会员信息集中存储，前台查询会员到期时间由翻阅纸质台账改为一次检索。

(2) 课程预约记录自动留存，减少因口头登记造成的漏记与争议。

(3) 工作人员在后台即可完成签到登记，无需额外硬件设备。

为什么这样改（以及只删连接词不够）

  • 「首先/其次/再者」是纯过渡词，删掉无损；但删完如果只剩「提高效率、降低成本、提升体验」， 就变成了三个空洞的标签，问题只是从「AI 味」变成了「没内容」。
  • 「(1)(2)(3)」比「第一第二第三」好，不只是格式问题： 中文段落里「第一、第二」是叙述式，容易被读成连续散文； 阿拉伯数字加括号是清单式，视觉上就宣告「这是并列要点」，更接近技术文档规范。
  • 关键在每条要点必须带一个受益对象 + 一个具体改善。 对照上表：好版本里出现了「前台」「纸质台账」「课程预约记录」「工作人员」「无需额外硬件」—— 全是可指认的名词。

2.3 系统架构设计 —— 定死 Spring Boot 3 + Vue3，删掉 React

修改前（典型写法）

后端采用 Spring Boot 框架，前端采用 Vue 或 React 等主流前端框架， 前后端通过 RESTful 接口交互，具有良好的扩展性。

修改后

系统采用前后端分离架构。后端使用 Spring Boot 3.5（JDK 17）+ MyBatis-Plus + MySQL 8.0， 提供 RESTful 接口；前端使用 Vue 3 + Element Plus + Vite，通过 axios 调用后端接口。

为什么这样改

  • 「Vue 或 React」是致命伤。技术选型写「或」等于告诉评审：我还没选，也没动手。 删掉 React 后选型唯一，是「已经开工」的信号。
  • 同类项目实测都是 Spring Boot 2.x（2.0.3 / 2.2.2 / 2.5.3），前端是 JSP/Bootstrap 或 Vue 2.6.10。 你写 Boot 3 + Vue3 属于领先，完全站得住 —— 但正因为领先，评审更可能追问细节。
⚠️ 写了 Boot 3 就必须补一句代价，否则是给自己挖坑

Spring Boot 3 有两个硬约束，答辩时大概率被问：

① 必须 JDK 17 起（Boot 2.x 的基线是 JDK 8）； ② javax.* 全部迁移到 jakarta.*， 老教程和多数现成代码直接抄过来会编译不过。

建议在开题报告里主动写一句：「后端基于 JDK 17 与 Spring Boot 3.5， 注意 jakarta.* 命名空间与 Boot 2.x 的差异」。 主动说出难点，比被问出来强得多 —— 这是「真做过」的最强信号。

你手上已经有 Boot 3 的真实项目经验（mall-swarm 是 jakarta 命名空间， 而 eladmin-mp 是 javax），这个对比正好可以当答辩素材。

2.4 系统需求分析 —— 「权限边界」→「三类角色权限」

修改前（典型写法）

系统需明确各角色的权限边界，实现细粒度的访问控制，保障数据安全与操作合规。

修改后

系统包含三类角色，权限划分如下：

管理员：会员管理、教练管理、课程管理、器材管理、预约记录管理；
教练：查看本人课程与预约名单；
会员：查看课程、预约课程、查看个人记录。

实证支撑：bsxj97 的 README 里角色划分就是 管理员、用户、教练；liujianview 的建表脚本里有独立的 coach（教练）表。 「三类角色」是这类项目的实际做法，不是我们臆造的。 bsxj97/gym-management-system README「角色：管理员、用户、教练」

为什么这样改

  • 「权限边界」「细粒度访问控制」「操作合规」是纯抽象词， 它们描述的是属性而不是内容 —— 追问「哪几个角色、各自能做什么」就答不上。 换成角色清单后，每个词都对应一个真实页面。
  • 更进一步：把角色和功能做成「角色—功能」表（如上）， 这张表直接就是后面「核心功能模块」和数据库「角色表」的草稿，一份内容复用三处。

2.5 核心功能模块 —— 删套话与复杂功能，简化为可交付的签到

修改前（典型写法）

实现会员全生命周期管理，覆盖从入会、预约、签到到续费、流失预警的完整闭环； 支持扫码签到、人脸识别入场、满员自动候补、订单自动核销等智能化功能。

修改后

实现会员管理、教练管理、课程管理、器材管理、课程预约与签到登记功能。

签到功能支持工作人员在后台为会员手动完成签到登记，记录签到时间与操作人。

实证支撑（这是整份材料里最硬的一条）
在 MiloTnT（355★，6 张表）、liujianview（222★，11 张表）、 bsxj97 的源码树与建表脚本中检索，结果全部为 0： 签到 0 · 人脸 0 · 扫码 0 · 核销 0 · 候补 0 · 微信 0 · 短信 0 · 二维码 0 而唯一实现了签到的 evangui（410★），形态是 一张 CheckinRecord 表 + 后台手工登记的增删改查。 guns-bizcore/.../model/CheckinRecord.java 含字段 opeUserId、opeUsername（操作人）

为什么这样改

  • 「全生命周期」是套话的典型结构：听起来很完整，但无法对应任何一张表。 它把「增删改查」包装成了「闭环」。删掉后改成五张业务表的名字，立刻具体。
  • 扫码签到 / 人脸识别 / 自动核销 = 外部依赖 + 硬件 + 资质， 毕设周期内做不完（人脸识别还要第三方 SDK、企业资质和费用）。删掉是务实，不是偷懒。
  • 「满员自动候补」是算法问题，涉及队列、通知、并发抢位，属于难点而非功能点。删掉合理。
  • 「支持签到功能 + 工作人员手动完成签到」这个改法非常好，因为它同时满足三个条件： 可交付（一张表 + 一个按钮）、可演示（答辩能当场点）、有实证（evangui 就是这么做的）。 注意 evangui 的表里有操作人字段，这恰好证明了「手动」是真实做法。
建议：把签到表设计写进开题报告（一行就够）

写了字段名，「具体确定」就落地了，而且答辩时可以直接讲：

-- 签到记录表（参照 evangui 的 CheckinRecord 简化） checkin_record( id -- 主键 member_id -- 会员 ID，外键关联会员表 checkin_time -- 签到时间 operator_id -- 操作人 ID（工作人员） operator_name -- 操作人姓名 remark -- 备注 )

2.6 后续内容 —— 删外部接口、改技术路线、去技术套话

(a) 删除短信、微信模板等外部接口依赖

修改前（典型写法）

系统通过短信接口向会员发送到期提醒，并接入微信模板消息推送预约通知。

修改后

会员到期与预约状态在系统内以列表和状态字段呈现，工作人员可据此查看与处理。

为什么删：短信和微信模板消息都需要第三方账号、企业资质、费用和审核流程 （微信模板消息还要求认证服务号）。这不是代码能力问题，是前置条件不具备。 实证上，五个同类项目里「微信」「短信」命中数均为 0。

替换技巧：把「推送通知」降级为「状态字段 + 列表查看」。 同一个业务价值（让会员知道要到期了），实现成本从「对接第三方」降到「一个 status 字段」。

(b) 技术路线：箭头改顿号/文字，并补上「每步产出物」

修改前（典型写法）

需求分析 → 数据库设计 → 后端开发 → 前端开发 → 系统测试

修改后

需求分析（产出用例图与角色功能表）、数据库设计（产出 E-R 图与表结构）、 后端接口开发（Spring Boot 3 + MyBatis-Plus）、前端页面开发（Vue 3 + Element Plus）、 联调测试（Postman 验证接口、浏览器验证页面）。

为什么这样改：纯箭头串是流程模板，任何项目都能套。 补上括号里的产出物后，它变成了你这套系统的执行计划 —— 评审能看出「E-R 图」和「Postman」这种具体工具名，说明确实做过。

(c) 删除「三层映射」「高并发控制」等技术套话

修改前（典型写法）

系统采用三层映射架构，并通过缓存与队列实现高并发控制，保障系统稳定性。

修改后

后端分为 Controller、Service、Mapper 三层：Controller 接收前端请求并校验参数， Service 处理业务逻辑，Mapper 负责数据库读写。

为什么删：

  • 「三层映射」是生造词。标准说法是「三层架构」（表现层 / 业务层 / 数据访问层）。 写「映射」说明是在堆词。改成分层职责描述后，每层都有具体动作。
  • 「高并发控制」是自曝短板。毕设系统没有并发场景，写了它就要回答 「QPS 多少」「压测过吗」「为什么用队列」—— 三个问题都答不上。 实证上，MiloTnT（355★）的作者自己在 README 里写： 第一次做项目，有很多想实现的功能碍于个人能力不够无法实现。 真实项目的作者都承认能力边界，你的开题报告没有理由声称高并发。

3这些功能到底能不能做 —— 逐项可行性判断

先澄清一个容易被误读的点：「同类项目没做」不等于「技术上做不到」。 第 1 节回答的是「别人做到哪一步」，本节回答的是「技术上能做到哪一步」。 两者混在一起会得出错误结论 —— 例如以为「人脸识别根本写不了」，这是不对的。

判断时要把三层门槛分开看：

  • 能写出代码 —— 这层几乎没有门槛，基本都是标准增删改查 + 现成库；
  • 能端到端跑起来 —— 这层开始卡外部条件：账号资质、审核、费用、硬件、网络环境；
  • 能上生产 —— 这层还要卡稳定性、合规与成本，毕设阶段不必考虑。

3.1 逐项判断

功能能否实现关键卡点大致范围开题报告建议
签到登记 ✅ 完整可做 无外部依赖 1 张表 + 增删改查 + 1 个页面，约 1 天 写（推荐表述：工作人员后台手动登记）
二维码生成 ✅ 完整可做 无外部依赖（后端 ZXing 或前端 qrcode 库） 约 2 小时 可写，但价值有限
扫码 ⚠️ 有条件可做 网页调摄像头要求 HTTPS 或 localhost，局域网 HTTP 下摄像头直接不可用；微信「扫一扫」需认证账号；扫码枪则是纯键盘输入，零代码成本 半天（网页方案） 谨慎写。若写，必须说明「在 HTTPS 环境或使用扫码枪」
核销 ✅ 完整可做 无外部依赖 —— 本质就是一次状态字段更新 半天 写，但不要写「自动核销」（见 3.2）
候补 ✅ 完整可做 无外部依赖（一张候补表 + 顺序字段 + 状态机）；但「自动递补通知」会撞到消息推送问题 2～3 天 可写，但需说明候补顺序规则（按申请时间排序）
人脸识别 ⚠️ 能做，但性价比低 百度智能云个人实名认证即可领 1000 次/月免费额度（1 QPS），人脸检测低至 0.0004 元/次；但活体检测个人仅 500 次免费，且引入外部网络依赖；本地开源模型则要跨语言（Python/OpenCV） 调云 API 约 2～3 天；本地模型 1～2 周 不建议写 —— 不是做不到，而是对毕设投入产出比太低
微信 ❌ 个人身份做不了 模板消息需认证服务号（300 元/年审核费 + 组织主体）；微信登录需开放平台网站应用（企业主体）；微信支付需商户号；个人主体小程序无法接入微信支付、无法获取手机号，且消息推送频次受限 — 删掉是正确的
短信 ⚠️ 只能做验证码 腾讯云自 2025-09-18 起不再支持新增个人认证用户申请短信签名；阿里云传统短信需签名归属方资质报备；阿里云「短信认证」（号码认证服务）个人实名即可、免签名报备，但只能用预置模板，且模板只含「验证码 + 有效期」两个变量 约 1 天 原报告写的「到期提醒」属于业务通知类 ⇒ 必须删；若改成「注册/登录验证码」则可留

※ 政策与价格数据核实于 2026-09-28，来源：百度智能云产品价格文档、阿里云帮助中心与开发者社区、 腾讯云公告（2025-09-12）、微信小程序开放能力文档。此类政策会变动，引用前请复核。

3.2 四个必须分清的区分（这决定了表述能不能写）

① 「生成二维码」和「扫码」是两个完全不同的难度。
生成二维码是纯本地库调用（后端 ZXing / 前端 qrcode），无任何外部依赖，成本近乎为零。 而扫码要调用摄像头，浏览器出于安全考虑要求页面运行在 HTTPS 或 localhost 下 —— 如果答辩演示时用局域网 HTTP 打开，摄像头会直接不工作。 这也是为什么很多项目改用扫码枪：它对系统而言只是一个键盘输入设备，零代码成本。
② 「核销」很简单，难的是「自动」。
核销的本质是把优惠券/订单的状态字段从「未使用」改成「已使用」—— 半天的活。真正复杂的是「自动核销」，它要求系统能自动判断核销时机， 通常依赖定时任务、消息队列或硬件回调，属于工程复杂度问题而非功能问题。 所以：「支持核销」可以写，「自动核销」不要写。
③ 「短信验证码」可做，「短信业务通知」做不了。
这是整份判断里最容易被忽略的一条。阿里云确实为个人开发者开了口子 （「短信认证」，个人实名即可、免签名报备），但只能用平台预置模板， 模板里只有「验证码」和「有效期」两个变量 —— 你没法把「您的会员将于 3 天后到期」塞进去。 因此：注册登录验证码可以做；到期提醒、预约通知这类业务通知做不了。 原开题报告写的正是后者，必须删。
④ 「人脸识别」的真正门槛是活体检测，不是识别本身。
百度智能云对个人实名认证开放了基础人脸能力（1000 次/月免费，1 QPS）， 人脸检测单价低至 0.0004 元/次 —— 调通它只需约 50 行代码。 但「刷脸入场」要防的是拿照片冒充，这需要活体检测， 而活体检测个人认证只有 500 次免费额度，单价 0.002～0.1 元/次。 换句话说：能演示「识别」，但演示不了「防作弊」， 而后者才是这个功能的意义所在。
⚠️ 对第 1 节结论的修正说明

第 1 节的结论「同类项目都没做这些功能」是事实陈述， 不构成「这些功能做不了」的可行性判断。两者不能互相替代。

正确的理解是：这些功能里，多数技术上可行，少数受资质限制不可行； 但它们的共同点是「投入产出比不适合毕设」 —— 要么需要外部账号资质，要么需要硬件或 HTTPS 环境，要么需要跨语言工程。 删掉它们的理由是范围控制，不是能力不足。 这个区别在答辩时很重要：前者是主动决策，后者是被动承认。

4你没提但必须补的 3 件事

4.1 版本号要写全 —— 包括 JDK

你要求把架构「确定为 Spring Boot 3 + Vue3」，这很好。但只写到这一层还不够， 因为「Spring Boot 3」隐含一个硬性前提：JDK 17 起。

建议直接写成一行完整的技术栈清单，比任何形容词都有说服力：

后端：JDK 17 · Spring Boot 3.5 · MyBatis-Plus · MySQL 8.0 前端：Vue 3 · Element Plus · Vite · axios 工具：Maven · IDEA · Navicat · Postman

对照实证：同类项目的技术栈说明都是这种「名词 + 版本」的清单形式 （如 liujianview 列出「SpringBoot / Spring Data JPA / MySQL / Maven / JSP / Shiro / Bootstrap,Layui / ECharts」）， 没有一个是形容词式描述。

4.2 把「不做什么」写进研究内容

你删掉了扫码签到、人脸识别、候补、自动核销、短信、微信。但直接删掉会在文本里留下空缺， 评审看到「功能变少了」可能理解为「能力不足」。

更好的做法是主动划边界，加一句：

本系统面向中小型健身房，聚焦会员、教练、课程、器材四类基础数据的管理与课程预约、签到登记， 不包含在线支付、门禁硬件对接与第三方消息推送功能。

这句话的作用是把「做不到」重新定义为「范围界定」 —— 范围明确的项目比功能泛泛的项目更容易通过，而且答辩时没人会追问你「为什么不做支付」。

4.3 补一张数据库表清单

这是「让内容具体确定」最有效的一招。删掉复杂功能后，「研究基本内容」到底剩什么？ 答案就是表。同类项目的表数很朴素：MiloTnT 6 张、liujianview 11 张。

删（这些词一出现就露馅）

  • 括号注释类：（全口径）、（广义上）、（此处指……）

⚠️ 一条必须记住的排查纪律

搜索返回空时，先跑一个已知能返回结果的正对照，再下结论。 本次实测中，中文代码搜索对「签到」返回空、对「会员」也返回空 —— 后者显然不可能， 因此判定是查询失效。若不验证就采信，会把「查询坏了」误判成「这类功能不存在」， 推理过程完全错误，只是结论碰巧对了。
